# Анализ и трансформация эпидемиологических данных в SQL (PostgreSQL)

## Описание проекта

Проект представляет собой комплекс аналитических SQL-скриптов для очистки, нормализации, когортной группировки и дифференциального анализа эпидемиологических временных рядов (на основе открытых данных Центра системных наук и инженерии Университета Джонса Хопкинса).

Исходные данные содержат кумулятивные (накопительные) показатели выявленных случаев заболеваний и смертности. Основная инженерная задача проекта — трансформировать накопительные ряды данных в детализированные суточные приросты с учетом различной степени гранулярности наблюдений (страновой уровень, региональный уровень и смешанный тип сбора данных), устранить аномалии и сформировать витрины данных для последующего анализа.

---

## Архитектура базы данных

База данных состоит из двух основных схем:

### 1. Схема `geo_info`
- **`countries`**: общая справочная информация о государствах (ISO-коды, наименование, численность населения, плотность, процент населения старше 65 лет, процент женского населения).
- **`regions`**: детализированная информация о регионах отдельных государств (внешний ключ на `countries.id`).
- **`disease_statistics`**: сопутствующая статистика по распространенности соматических и инфекционных заболеваний.

### 2. Схема `covid`
- **`daily_statistics`**: журнал ежедневных кумулятивных наблюдений.
  - `country_id`: идентификатор страны (FK -> `geo_info.countries.id`).
  - `region_id`: идентификатор региона (FK -> `geo_info.regions.id`, может быть `NULL`).
  - `observed_date`: дата фиксации наблюдения.
  - `confirmed`: кумулятивное количество выявленных случаев на дату.
  - `deaths`: кумулятивное количество летальных исходов на дату.

## Спецификация заданий и логика решений

### Задание 1. Демографическая фильтрация (`src/task_1.sql`)
- **Цель**: выборка стран с населением свыше 100 000 000 человек и долей пожилого населения (65+) более 10%.
- **Поля вывода**: `name`, `population`, `density`.
- **Особенности**: округление плотности населения до двух знаков после запятой (`ROUND(CAST(density AS numeric), 2)`), сортировка по убыванию плотности.

### Задание 2. Анализ структуры регионального покрытия (`src/task_2.sql`)
- **Цель**: определение распределения стран по наличию информации о регионах.
- **Группы**:
  1. `all` — все страны в базе.
  2. `yes` — страны, для которых зарегистрированы регионы.
  3. `no` — страны, для которых региональные данные отсутствуют.
- **Поля вывода**: `is_info_regions`, `count_country`.
- **Особенности**: объединение через `UNION`, применение `LEFT JOIN` для выявления стран без регионов, строгая фиксация порядка вывода (`all` -> `yes` -> `no`).

### Задание 3. Идентификация стран смешанного типа (`src/task_3.sql`)
- **Цель**: поиск стран 3-й группы, по которым в разные даты статистика поступала как на уровне отдельных регионов, так и на уровне страны в целом.
- **Поля вывода**: `id`, `name`.
- **Ограничение**: использование исключительно операторов `JOIN` и `WHERE` (без `GROUP BY`, подзапросов в `WHERE` и агрегатных функций).
- **Сортировка**: по возрастанию наименования страны (`c.name ASC`).

### Задание 4. Идентификация стран с региональной гранулярностью (`src/task_4.sql`)
- **Цель**: поиск стран 2-й группы, для которых абсолютно все наблюдения проводились на уровне регионов (`region_id IS NOT NULL`).
- **Поля вывода**: `id`, `name`.
- **Особенности**: применение группировки `GROUP BY` и фильтрации `HAVING COUNT(ds.region_id) = COUNT(*) AND COUNT(*) > 0`.
- **Сортировка**: по алфавиту (`c.name ASC`).

### Задание 5. Идентификация стран со страновой гранулярностью (`src/task_5.sql`)
- **Цель**: поиск стран 1-й группы, где фиксация данных всегда велась только в целом по стране (`region_id IS NULL`).
- **Поля вывода**: `id`, `name`.
- **Особенности**: группировка по стране с условием `HAVING COUNT(ds.region_id) = 0`.
- **Сортировка**: по алфавиту (`c.name ASC`).

### Задание 6. Дифференциация ряда для 1-й группы (`src/task_6.sql`)
- **Цель**: расчет ежедневного числа заболевших (`confirmed_by_day`) и умерших (`deaths_by_day`) по странам 1-й когорты.
- **Поля вывода**: `country_id`, `observed_date`, `confirmed_by_day`, `deaths_by_day`.
- **Особенности**: отбор стран через подзапрос с предикатом `IN`. Вычисление разницы между текущим днем и предыдущим днем через самосоединение (`LEFT JOIN ... ON cur.observed_date - 1 = prev.observed_date`). Значение предыдущего дня обрабатывается через `COALESCE(prev, 0)`.
- **Сортировка**: `country_id, observed_date`.

### Задание 7. Агрегация и дифференциация для 2-й группы (`src/task_7.sql`)
- **Цель**: расчет суточных приростов для стран 2-й когорты.
- **Поля вывода**: `country_id`, `observed_date`, `confirmed_by_day`, `deaths_by_day`.
- **Особенности**: использование конструкции `WITH` (Common Table Expressions, CTE). На первом шаге данные всех регионов суммируются до уровня страны на каждую дату, на втором шаге выполняется самосоединение для расчета дельт.
- **Сортировка**: `country_id, observed_date`.

### Задание 8. Многостадийная нормализация смешанных данных (`src/task_8.sql`)
- **Цель**: расчет приростов для наиболее сложной 3-й группы стран.
- **Архитектура решения**: использование временных таблиц (`CREATE TEMP TABLE`):
  1. `tmp_group3_countries`: выборка идентификаторов целевых стран.
  2. `tmp_group3_regional`: суммирование региональных срезов по странам и датам.
  3. `tmp_group3_country`: выборка общегосударственных срезов.
  4. `tmp_group3_unified`: слияние через `FULL OUTER JOIN` с приоритетом региональных агрегатов через `COALESCE`.
  5. Итоговый `SELECT`: расчет суточных приростов через соединение со смещением на 1 день.

### Задание 9. Создание представлений (`src/task_9.sql`)
- **Цель**: инкапсуляция логики трех когорт в повторно используемые виртуальные таблицы:
  - `covid.daily_statistics_country_level` — для 1-й когорты.
  - `covid.daily_statistics_region_level` — для 2-й когорты.
  - `covid.daily_statistics_mix` — для 3-й когорты.

### Задание 10. Построение физической витрины данных (`src/task_10.sql`)
- **Цель**: объединение потоков данных из трех представлений в физическую таблицу `covid.daily_statistics_recalculated`.
- **Очистка данных**:
  - Отрицательные значения суточных приростов (возникающие из-за ретроспективных корректировок в исходных отчетах) заменяются на `0`:
    ```sql
    CASE WHEN confirmed_by_day < 0 THEN 0 ELSE confirmed_by_day END
    ```
  - Значения `NULL` сохраняются без изменений в соответствии с регламентом обработки пропущенных данных.
- **Объединение**: оператор `UNION ALL`.

### Задание 11. Оконные функции: нарастающий итог (`src/task_11.sql`)
- **Цель**: восстановление кумулятивного ряда подтвержденных случаев и верификация обратной сходимости данных.
- **Поля вывода**: `country_id`, `observed_date`, `confirmed_cumulative`.
- **Особенности**: оконная агрегация:
  ```sql
  SUM(confirmed_by_day) OVER (PARTITION BY country_id ORDER BY observed_date)
  ```

### Бонусное задание 1. Пиковые значения заболеваемости (`src/task_bonus_1.sql`)
- **Цель**: нахождение даты и величины максимального суточного прироста выявленных случаев для каждого государства.
- **Поля вывода**: `name`, `observed_date`, `confirmed_by_day`.
- **Особенности**: аналитическое ранжирование через оконную функцию `ROW_NUMBER() OVER (PARTITION BY r.country_id ORDER BY r.confirmed_by_day DESC, r.observed_date ASC)` с последующей фильтрацией первой строки (`WHERE rn = 1`) и сортировкой по имени страны.

## Валидация и контрольные метрики

Для проверки корректности сборки витрин данных используются следующие контрольные соотношения:

1. **Контроль объема строк физической таблицы**:
   Количество записей в `covid.daily_statistics_recalculated` должно строго совпадать с числом уникальных комбинаций `(country_id, observed_date)` в исходной таблице `covid.daily_statistics`:
   ```sql
   SELECT COUNT(*) FROM covid.daily_statistics_recalculated;
   -- Результат: 195 000 строк

   SELECT COUNT(DISTINCT (country_id, observed_date)) FROM covid.daily_statistics;
   -- Результат: 195 000 строк
   ```

2. **Контроль компонентного состава витрины**:
   - 1-я группа (страновой уровень): 169 625 строк.
   - 2-я группа (региональный уровень): 6 090 строк.
   - 3-я группа (смешанный уровень): 19 285 строк.
   - Итого: `169625 + 6090 + 19285 = 195000`.

3. **Сходимость нарастающего итога**:
   Значение `confirmed_cumulative` из `task_11.sql` на каждую дату полностью соответствует оригинальным значениям поля `confirmed` таблицы `covid.daily_statistics`.
